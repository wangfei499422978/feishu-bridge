# Feishu Bridge

A Feishu long-connection bridge: it receives a user's messages in real time
over Feishu's official outbound WebSocket (long-connection event mode), logs
them, and reacts instantly. It was built to chat with Muse inside Feishu,
which has no native Feishu connector.

## Files

- `receiver.py` — WebSocket receiver. Subscribes to `im.message.receive_v1`,
  appends accepted messages to `events.log`, and adds an instant THUMBSUP
  reaction to each accepted message as a "received" signal.
- `send_reply.py` — small helper to send a manual text reply through the
  Feishu reply API (used for testing and one-off replies).

## Features

- Persistent message_id dedup: accepted ids are stored in `seen_ids.json`
  (plus a seed from `answered.txt` at startup), so reconnects and restarts
  never reprocess the same message.
- Staleness skip: messages older than 15 minutes are skipped, not answered.
- Own-message filter: ready but off unless the bot's own open_id is
  configured (`FEISHU_BOT_OPEN_ID`).
- Instant reaction: the THUMBSUP reaction is sent inside the event callback,
  so it lands in 1–3 seconds, independent of any reply pipeline.
- Proxy workaround: `lark-oapi` 1.7.5 hardcodes `proxy=None` for its WS
  client, which breaks in environments where only an HTTP(S) proxy reaches
  the internet. Setting `FEISHU_WS_USE_ENV_PROXY=1` drops that override so
  the WebSocket client discovers the proxy from environment variables.

## Setup

Requirements: Python 3.10+, `lark-oapi` 1.7.5.

1. Create a Feishu app, enable long-connection (event subscription) mode,
   and subscribe to `im.message.receive_v1`.
2. Store the app credentials in a restricted local config file named
   `.feishu-credentials` next to `receiver.py` (mode `0600`):
   `FEISHU_APP_ID` and `FEISHU_APP_SECRET`, one per line. Values are never
   printed or logged. Environment variables of the same names work as a
   fallback.
3. Run the receiver:

```sh
FEISHU_WS_USE_ENV_PROXY=1 python3 receiver.py >> events.log 2>&1
```

Accepted messages appear in `events.log` as `EVENT im.message.receive_v1`
lines; skipped messages appear as `SKIP` lines.

## Text replies

The receiver itself only handles receipt, dedup, and reaction. In the
original deployment, text replies are generated by Muse through a
runtime hook that polls `events.log` for new message ids (that hook is
Muse-runtime-specific and is not part of this repository). Any reply
pipeline can consume the `EVENT` lines from `events.log` and mark
answered ids in `answered.txt`.

## Not in this repository

Credentials, event logs, answered-message records, and dedup stores are
deliberately excluded (see `.gitignore`): `.feishu-credentials`,
`events.log`, `answered.txt`, `seen_ids.json`. Never commit them.
